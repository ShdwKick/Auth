# Как подключить сервис к единому аккаунту BurningHouse

Пошаговое руководство: что сделать, чтобы новый проект пускал людей через
`auth.burninghouse.ru` вместо собственного логина.

Рабочий пример целиком — в [examples/minimal-service/](examples/minimal-service/):
это настоящий запускаемый сервис на ~120 строк, из которого можно копировать.
Живой пример побольше — «Мои финансы» (`../Финансы`).

## Что происходит при входе

Упрощённый OAuth2 authorization code + PKCE. Пароль никогда не проходит через
ваш сервис — он вводится только на auth-домене.

```
1. Пользователь жмёт «Войти»
2. Фронт уводит его на  auth.burninghouse.ru/authorize?client_id=…&code_challenge=…
3. На auth-домене уже есть кука сессии?
      да  → мгновенный редирект обратно (это и есть SSO: пароль не спрашивают)
      нет → форма входа, после успеха ставится кука
4. Возврат: ваш-домен/?code=<одноразовый>&state=…
5. Фронт меняет код на токены:  POST /oauth/token
      → access-JWT (15 мин) + refresh (60 дней)
6. Фронт шлёт access в ваш API как  Authorization: Bearer …
7. Ваш бэкенд проверяет подпись САМ, по ключам из /.well-known/jwks.json
```

Пункт 7 — главное архитектурное решение: **на каждый запрос к вашему API в auth
никто не ходит**. Ключи кэшируются на час, подпись проверяется локально за
микросекунды. Поэтому auth не становится ни узким местом, ни единой точкой отказа:
если он ляжет, ваш сервис продолжит работать с уже выданными токенами.

Плата за это — отзыв доступа срабатывает не мгновенно, а когда истечёт текущий
access-токен (максимум 15 минут). Если нужно «прямо сейчас» — на auth-сервере
есть `rotate-key`, он обнуляет все выданные токены разом.

## Быстрый старт: 5 шагов

### 1. Зарегистрировать сервис в auth

```bash
docker compose exec auth node server.js client-add notes "Заметки" https://notes.burninghouse.ru/
```

Аргументы: `<client_id>` `<название для формы входа>` `<адрес возврата>`.

`redirect_uri` сверяется **побайтово** — лишний или пропущенный слэш, `http`
вместо `https`, `www.` — и вход не сработает. Это не придирка: свободный
redirect_uri означал бы, что любой сайт может увести к себе код авторизации.
Посмотреть, что записано: `node server.js clients`.

### 2. Скопировать две библиотеки

Обе — из этого репозитория, зависимостей у них нет:

| Файл | Куда | Зачем |
|---|---|---|
| `client/auth-client.js` | рядом с вашим `server.js` | проверка токена на бэкенде |
| `client/auth-client-browser.js` | в `assets/` вашего фронта | вход, обновление токена, `fetch` |

Копия, а не npm-пакет — по той же причине, по которой во всех этих проектах нет
`node_modules`. Файлы маленькие; если поменяются — скопировать заново.

### 3. Задать окружение

```yaml
environment:
  AUTH_ISSUER: https://auth.burninghouse.ru   # обязательно
  AUTH_CLIENT_ID: notes
labels:
  # чтобы Watchtower на сервере обновлял контейнер сам, когда вы запушите новый образ
  com.centurylinklabs.watchtower.enable: "true"
```

`AUTH_ISSUER` должен совпадать с `ISSUER` auth-сервиса **символ в символ** — он
подписан внутрь токенов и сверяется буквально.

Метка Watchtower — почему она вместо деплоя по SSH: сервер сам забирает новый образ
из Docker Hub, поэтому проекту не нужен ни SSH-ключ в секретах, ни деплой-скрипт.
Достаточно `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN` в GitHub Actions. Подробнее —
`README-deploy.md`, шаг 7.

### 4. Бэкенд — проверять токен

См. [Серверная часть](#серверная-часть).

### 5. Фронт — уводить на вход

См. [Клиентская часть](#клиентская-часть).

## Серверная часть

```js
const auth = require("./auth-client")({
  issuer:   process.env.AUTH_ISSUER,      // https://auth.burninghouse.ru
  audience: process.env.AUTH_CLIENT_ID,   // notes
});

// Подтянуть ключи заранее, чтобы первый запрос не ждал сеть.
// Ошибка тут не фатальна: ключи подтянутся при первом обращении.
auth.warmup();
```

Дальше в любом защищённом обработчике:

```js
const user = await auth.userFromRequest(req);
if (!user) return json(res, 401, { error: "unauthorized" });

// user = {
//   id:        "d082f00d-…",   // стабильный UUID — ЭТО и кладём в свои таблицы
//   username:  "danil",         // может измениться в будущем, ключом не делать
//   name:      "Данил" | null,  // есть, только если сам пользователь включил
//                                // показ в кабинете BurningHouse — иначе null
//   email:     "d@example.com" | null,
//   sid:       "…",             // id сессии, если нужен для логов
//   clientId:  "notes",
//   expiresAt: 1785404536000,
// }
```

Показывая, кто вошёл ("Вы вошли как …", подпись в шапке и подобное), берите
`user.name || user.username` — не один `username`. Так уважается решение
пользователя показывать имя вместо логина, принятое им один раз в общем
кабинете и действующее сразу во всех сервисах.

Что `auth-client` проверяет сам: алгоритм подписи (только `EdDSA` — подменить на
`none` или на HMAC не получится), саму подпись, `iss`, `aud`, `exp`/`nbf` с
допуском 30 секунд на расхождение часов. Незнакомый `kid` (ключ ротировали)
приводит к однократному перезапросу JWKS, не чаще раза в 30 секунд.

Отдайте фронту адрес auth, чтобы он не был зашит в статику:

```js
if (p === "/api/config") {
  return json(res, 200, { authBase: process.env.AUTH_ISSUER, clientId: process.env.AUTH_CLIENT_ID });
}
```

Ничего секретного тут нет: и адрес, и `client_id` всё равно видны в адресной
строке при входе. Смысл в том, чтобы менять их одной переменной окружения.

### Что НЕ нужно делать на бэкенде

- Не проксировать логин/пароль — их не должно быть в вашем коде вообще.
- Не звать `/api/userinfo` на каждый запрос: всё нужное уже в токене.
- Не делать свою таблицу пользователей. Максимум — профиль, привязанный к `user_id`.

## Клиентская часть

```html
<script src="assets/auth-client.js"></script>
```

```js
const cfg = await (await fetch("/api/config")).json();
const auth = createAuthClient({
  authBase: cfg.authBase,
  clientId: cfg.clientId,
  redirectUri: location.origin + location.pathname,  // ровно то, что в client-add
  storagePrefix: "notes",                            // префикс ключей в localStorage
});

// Вернулись со страницы входа с ?code=… → обменять на токены.
// Код из адресной строки убирается внутри, в истории браузера не остаётся.
await auth.handleRedirect();

if (!auth.isAuthenticated()) {
  auth.login();     // уводит на страницу входа
  return;
}

// Дальше — обычный fetch, только через auth.fetch
const res = await auth.fetch("/api/notes");
```

`auth.fetch` подставляет токен, а протухший обновляет молча и повторяет запрос
один раз. Если обновить нечем (refresh отозван или истёк) — бросает
`AuthRequiredError`; это единственный случай, когда пользователя надо вернуть
на вход:

```js
try {
  const res = await auth.fetch("/api/notes");
} catch (e) {
  if (e.name === "AuthRequiredError") return showLoginScreen();
  throw e;
}
```

Остальные методы:

```js
auth.getUser()      // { id, username, email } из последнего ответа токен-эндпоинта
auth.accountUrl()   // ссылка на кабинет: пароль, почта, устройства — всё там
auth.logout()       // отзывает refresh и уводит на выход из общего аккаунта
auth.login({ prompt: "login" })   // заставить ввести пароль, даже если есть SSO-кука
```

### Порядок на старте важен

`handleRedirect()` должен выполниться **до** первого запроса к вашему API —
иначе первый запрос уйдёт без токена и получит 401 на пустом месте:

```js
// правильно
await initAuth();          // внутри: fetch(/api/config) → createAuthClient → handleRedirect
await loadData();

// неправильно
loadData();                // ушёл без токена
await initAuth();
```

### Смену пароля у себя не делать

Пароль, почта и список устройств живут в кабинете на auth-домене. Ведите туда
ссылкой (`auth.accountUrl()`) — так это выглядит для пользователя одним аккаунтом,
а не набором похожих форм в каждом проекте.

## Хранение user_id

Ключом во всех своих таблицах должен быть `user.id` — UUID, который не меняется
никогда. `username` для этого не подходит: он может измениться, и тогда данные
«потеряют» владельца.

```sql
CREATE TABLE notes (
  id      TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,     -- user.id из токена
  ...
);
CREATE INDEX idx_notes_user ON notes(user_id);
```

`username` можно хранить рядом — как подпись в интерфейсе или чтобы было понятно,
чья строка при отладке. Но искать и связывать — только по `user_id`.

**Если сервис уже существует и держал пользователей по логину** — как это было с
«Финансами» — переезд делается лениво, без простоя: логин есть в токене
(`preferred_username`), поэтому при первом обращении можно перенести строку с
логина на `user_id`. Готовая реализация — `getState()` в `../Финансы/server.js`,
а история переезда — в `../Финансы/AUTH-INTEGRATION.md`.

## Чек-лист перед выкатом

- [ ] `client-add` выполнен, `clients` показывает верный `redirect_uri` (со слэшем!)
- [ ] `AUTH_ISSUER` совпадает с `ISSUER` auth-сервиса символ в символ
- [ ] `redirectUri` на фронте совпадает с зарегистрированным
- [ ] `origins` клиента включает домен фронта — иначе CORS отобьёт `/oauth/token`
- [ ] `handleRedirect()` вызывается до первого запроса к API
- [ ] Свои таблицы завязаны на `user_id`, не на логин
- [ ] Запрос без токена возвращает 401, а не пустые данные
- [ ] Проверено, что после `docker restart` вашего контейнера вход не теряется
- [ ] В compose есть метка `com.centurylinklabs.watchtower.enable` — иначе новый образ
      придётся выкатывать руками
- [ ] В секретах репозитория только `DOCKERHUB_*`; SSH-ключа там быть не должно

## Если что-то не работает

**«Сервис не зарегистрирован в auth»** на странице входа — не сделан `client-add`,
либо `client_id` на фронте не тот.

**«redirect_uri не совпадает…»** — сверьте побайтово с выводом `clients`. Чаще
всего виноват завершающий слэш или `location.pathname`, отличающийся от
ожидаемого (`/index.html` вместо `/`).

**Все запросы к вашему API отвечают 401.** Почти всегда — расхождение
`AUTH_ISSUER` и `ISSUER`. Проверьте прямо в токене:

```bash
# payload JWT читается без ключей — там видно, какой iss и aud внутри
node -e 'console.log(JSON.parse(Buffer.from(process.argv[1].split(".")[1],"base64url")))' <ваш-access-token>
```

**Вход проходит, но сразу выкидывает обратно.** Кука сессии помечена `Secure` и по
`http://` не отдаётся. В проде открывайте `https://`, а nginx должен передавать
`X-Forwarded-Proto https`. Локально по http — переменная `DEV=1` у auth-сервиса.

**CORS-ошибка на `/oauth/token`.** Домена фронта нет в `origins` клиента. Добавьте:
`client-add <id> <название> <redirect-uri> https://ваш-домен`.

**Токен принимается дольше, чем ожидалось после `exp`.** Так и задумано: допуск на
расхождение часов 30 секунд применяется и к `exp`. Настраивается параметром
`clockSkew` при создании клиента (в «Финансах» — переменная `AUTH_CLOCK_SKEW`).

**Ключи ротировали, сервис отвечает 401.** Должно вылечиться само в пределах
30 секунд (перезапрос JWKS при незнакомом `kid`). Если нет — проверьте, что
сервис вообще достаёт `/.well-known/jwks.json` со своей машины: в Docker
`localhost` — это сам контейнер, для соседнего нужен `host.docker.internal` или
имя сервиса compose. Задаётся отдельно через `AUTH_JWKS_URL`.

## Что делать НЕ надо

- **Не проверяйте токен через запрос в auth на каждый вызов.** Смысл JWT ровно в
  том, чтобы этого не делать. `/api/userinfo` существует для разовых сценариев.
- **Не храните access-токен в куке своего домена.** Он живёт в `localStorage`
  и уходит явным заголовком — так нет ни CSRF, ни проблем со scoping между поддоменами.
- **Не увеличивайте `ACCESS_TTL` до дней.** Короткий срок — единственное, что
  ограничивает окно отзыва; долгую жизнь сессии обеспечивает refresh-токен.
- **Не изобретайте свой refresh.** Ротацию и распознавание кражи токена
  клиентская библиотека уже умеет.
- **Не завязывайтесь на `username` как на ключ.** См. [выше](#хранение-user_id).

## Справочник API

Всё, что нужно сервису. Полный список — в `server.js` auth-сервиса.

| Метод и путь | Кто зовёт | Что делает |
|---|---|---|
| `GET /authorize` | браузер (переход) | `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256`, опц. `prompt=login`. Отдаёт форму входа или сразу редиректит с кодом |
| `POST /oauth/token` | фронт сервиса | `grant_type=authorization_code` (+`code`, `code_verifier`, `client_id`, `redirect_uri`) либо `grant_type=refresh_token` (+`refresh_token`, `client_id`) → `{access_token, refresh_token, expires_in, user}` |
| `POST /oauth/revoke` | фронт сервиса | `{refresh_token}` → отзыв. Всегда отвечает `ok` |
| `GET /.well-known/jwks.json` | бэкенд сервиса | публичные ключи; кэшировать час |
| `GET /api/userinfo` | по Bearer | `{id, username, email, name}` — `name` только если включён показ |
| `GET /logout` | браузер (переход) | гасит сессию; `post_logout_redirect_uri` — только на зарегистрированный origin |
| `GET /.well-known/openid-configuration` | — | адреса всех эндпоинтов |

Структура access-токена:

```json
{
  "iss": "https://auth.burninghouse.ru",
  "sub": "d082f00d-a9db-4f59-9e3c-bff97ab1ece6",
  "aud": "notes",
  "preferred_username": "danil",
  "name": "Данил",
  "email": "d@example.com",
  "sid": "…", "iat": …, "nbf": …, "exp": …, "jti": "…"
}
```

`name` и `email` — необязательные claims, в токене их может не быть вовсе
(email не указан, имя не включено к показу). Не полагайтесь на их наличие.
